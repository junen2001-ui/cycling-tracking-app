# 朝食ライド ルート提案 MVP 仕様書

## 概要
既存のサイクリングイベント管理アプリ(以下「本体アプリ」)の技術資産を流用し、
数人での朝食ライド向けに「開いている店を探す + そこまでのルートを提案する」機能を
MVPとして切り出して開発する。

将来的には本体アプリへの統合、および複数ユーザーのライドログを蓄積した
ルート推薦機能への拡張を見据える。

---

## 1. API選定

### 店舗検索: Google Places API
- 無料枠($200クレジット/月)内での運用を前提とする
- Nearby Search / Text Search を使用し、カフェ・モーニング提供店を検索
- 営業時間データを取得し、フィルタリングに使用

### ルート生成: Google Directions API
- 基本は bicycling モードでルート生成
- bicycling モードで実用的なルートが得られない場合(地方エリア等)のフォールバック:
  - driving モードを使用
  - waypoint調整により、幹線道路(primary/trunk)を避ける疑似ルーティングを実装
  - 精度は「多少雑でも可」とする。MVP段階では完璧なルーティングを追求しない
- 往復ルートは行きと帰りで別waypointを設定し、できるだけ異なる道を通る
  周回ルートとして生成する(単純な往復折り返しは避ける)

### 標高データ: Google Elevation API(または Directions API のレスポンスに含まれる標高情報)
- 出発地〜店舗〜出発地の往復ルート全体の獲得標高(累積上昇量、行き+帰りの合計)を算出
- 候補店舗表示・ルート表示それぞれで往復の獲得標高を提示する
- ルート表示画面では、距離に対する標高の推移を示す高度プロファイルグラフを表示する
  (一定間隔でElevation APIから標高をサンプリングし、行き→帰り通しの折れ線として描画)
- グラフ描画ライブラリ: React Native Wagmi Charts を使用する(MVPは実装スピード優先。
  将来デザインを作り込みたくなった場合は Victory Native への置き換えを検討)

### 将来拡張(MVP時点では設計の余白として意識)
- 過去に生成・実走したルートをレコメンドに活用できるよう、
  ルートデータは後から検索・再利用しやすい形で保存しておく

### コスト管理
- Claude Codeでの実装時、API呼び出し回数をログ・カウントできる仕組みを入れる
  (例: 呼び出しごとにDBまたはログファイルにカウント記録し、
  管理画面 or CLIコマンドで「今月の使用量目安」を確認できるようにする)
- $200枠を超えない設計を基本方針とし、閾値に近づいた場合の警告なども検討候補とする
  (MVPでは必須ではないが、カウント基盤は最初から作っておく)

## 2. データモデル骨子

余白を持たせ、後から項目追加しやすい設計とする(JSONBカラムの活用等も検討)。

### Route
- id
- start_location (lat/lng)
- start_time
- distance_km (希望距離)
- elevation_gain_m (往復の獲得標高。行き+帰りの合計)
- elevation_profile (JSONB: 距離ごとの標高サンプル配列。グラフ描画用)
- outbound_path (行きのルートデータ)
- return_path (帰りのルートデータ。行きとは別ルート)
- created_at
- selected_shop_id (FK → Shop)
- gpx_file_path (生成したGPXの保存先。任意項目 / null許容)
- shared_at (グループ共有した日時。GPX保存とは独立して記録)
- ※将来拡張用: source_route_id (過去ルートを参考にした場合の参照)

### Shop
- id
- name
- location (lat/lng)
- elevation_gain_round_trip_m (出発地からの往復獲得標高。ルート生成時に算出しキャッシュ)
- opening_hours (Google Places由来。取得不可の場合は null)
- has_morning_set (bool, 手動タグ想定)
- tags (配列 or JSONB。将来のコミュニティタグ拡張を見込む)
- rating (Google Places由来)
- opening_hours_verified (bool。営業時間データの信頼度フラグ)
- created_at / updated_at
- ※訪問済み判定は Shop に持たせず、Route テーブルに selected_shop_id が
  紐づいているかどうかで判定する(候補検索時に除外・履歴表示に使用)

### RideLog(将来蓄積用。MVPではテーブルのみ用意)
- id
- route_id (FK → Route)
- actual_gpx_path
- feedback (JSONB: 走りやすさ・車の多さ・景色等、多軸評価を見込む)
- created_at

### ApiUsageLog(コスト管理用)
- id
- api_name (Places / Directions)
- called_at
- (必要に応じて) cost_estimate

## 3. 基本フロー(画面遷移)

1. **出発地点入力**
   - 地図タップで指定
   - 過去の履歴(直近使用した出発地点)からも選択可能
2. **条件指定**
   - 希望距離
   - 出発時刻(希望時間帯)
3. **候補店舗表示**
   - 5件程度表示
   - 表示項目: 店名・距離・往復の獲得標高・営業時間・評価
   - 到着予想時刻に営業時間データが無い店舗は「営業時間不明」として
     候補には含めつつ、その旨をユーザーに明示する
   - 既に訪問済みの店舗は新規候補からは除外する
   - 画面下部に「過去に行った店を見る」ボタンを配置(デフォルトは折りたたみ)
     - 展開すると過去に訪問した店舗一覧を表示
     - 各店舗をタップすると、その時に使用したルート・獲得標高等を
       地図上で確認できる(今回の希望距離と異なっていても参考として表示する)
4. **店舗選択**
   - ユーザーが1件を選択
5. **ルート表示**
   - 地図表示
   - 距離・所要時間目安・往復の獲得標高(行き+帰りの合計)を表示
   - 高度プロファイルグラフを表示(横軸: 距離、縦軸: 標高。行き・帰り通しで
     推移が分かる形にする)
   - 行きと帰りはできるだけ異なる道を通るルートを生成する(周回ルート優先)
6. **(任意)グループ共有**
   - GPXファイルの保存有無に関わらず、確定したルートをグループメンバーに共有可能
     (本体アプリの共有機構を流用想定)
7. **GPXファイル保存(任意)**
   - 生成したルートをGPX形式でエクスポート・保存
   - 共有とは独立した任意ステップとする

---

## 4. 営業時間フィルタ仕様

- ロジック: 「出発時刻 + (希望距離 ÷ 想定巡航速度)」で各店舗への到着予想時刻を算出し、
  その時刻に営業中の店舗のみを基本候補とする
- Google Placesの営業時間データが取得できない/不正確な可能性がある店舗については、
  除外せず候補に含めた上で「営業時間情報が確認できません」という表示を行う
  (ユーザー自身の判断に委ねる形にする)

## 5. 技術スタック

本体アプリと同一スタックを継続使用する。

- フロントエンド: React Native / Expo
- バックエンド: Node.js
- DB: PostgreSQL / PostGIS
- リアルタイム通信: Socket.io(共有機能で必要に応じ流用)
- 地図表示: react-native-maps 等、本体アプリの実装方式を踏襲(要確認)

---

## 6. コスト上限の意識(実装方針)

- 月間$200枠を超えないことを前提としつつ、
  Claude Codeでの実装時には以下を意識した設計とする:
  - Places API / Directions API それぞれの呼び出し回数をログに記録
  - 呼び出し回数・概算コストを可視化できる簡易な仕組み(管理画面 or ログ集計)を用意
  - 不要な重複呼び出し(同一条件での再検索等)を避けるキャッシュ戦略も
    実装フェーズで検討する

## 備考・今後の検討事項

- Google/OSMの自転車ルートモードは地方エリアではデータが薄いため、
  MVP以降、走行ログの蓄積が進んだエリアから手動登録ルートやコミュニティデータへの
  比重を上げる方針とする
- 複数ユーザーのライドログ・フィードバックを蓄積し、
  将来的にエリア別・脚質別のルート推薦機能へ拡張する
